The second entry today. [`2026-08-17.md`](2026-08-17.md) handed Plan 2 over for redesign; this
one reports the plan that replaced it, executed end to end.

## Where things stand

**`mendel-forge` exists, and it calls no model.** Twenty-three tasks, seven checkpoints, all
run. `make verify` is green. The package is the first entry in `IMPURE_PACKAGES`, and
`test_no_pure_package_imports_an_impure_one` holds the arrow pointing at the pure packages and
never back.

The loop is `discover → draft → show → fill → verify → land`, over one operations layer with two
transports. [`docs/guides/driving-the-forge.md`](../../guides/driving-the-forge.md) is that
loop with real output; `ARCHITECTURE.md` §10 is the description against the types;
[`the spec`](../specs/2026-08-16-the-forge.md) is why each part is shaped the way it is.

**What is next is Phase 2**, and the whole of the next section is written for whoever starts it.

# Phase 2 — everything you need before writing a line of it

Written on the day Phase 1 merged, by the agent that built it, for the agent that will not have
been here. Read this section, then `notes/specs/2026-08-16-the-forge.md` §10, then
`packages/mendel-forge/src/mendel_forge/ports.py` — which is nine lines and is the whole seam.

## 0. Answer the fifth-door question first. It is not an implementation question.

**Invariant 14 says data leaves through four declared doors and no others.** They are goal
extraction, tier-4 resolution, compiler repair, and publication — `DOORS` in
`comeni_core/artifact/egress.py`, and `tests/test_egress.py` holds the list literally so that
widening the boundary means editing a test that says *these are all the ways data leaves*.

**A forge model call is a fifth crossing.** It sends a tool's `meta.yml` prose, its process
declaration and a list of candidate values to a provider. That is not patient data and never can
be — invariant 15 holds, because the forge reads vendored modules and registry files and has no
input that accepts a sample. But it is *data leaving a declared boundary*, and the invariant does
not say "no patient data leaves"; it says data leaves through four doors and enumerates them.

So exactly one of these has to happen, in the open, before an adapter exists:

1. **The forge's call becomes door 5.** `DOORS` gains an entry, `test_egress.py` gains a payload
   type, and that payload is closed vocabulary like the other four — no `Any`, no bare `str`,
   every string a declared ID alias or marked `Mark.FREE_TEXT`. Note that a `Hole` today carries
   `what`, `why_open` and `Excerpt.text`, all of which are free prose, so the payload type is
   real work rather than a rename.
2. **The argument is written that it is not egress**, and invariant 14's wording is tightened to
   say what it actually means — probably something about *pipeline* data rather than all data.
   This is defensible and it is not free: the invariant's current strength comes from being
   absolute, and a carve-out is the thing future carve-outs will cite.

**Do not write a `HoleFiller` implementation before this is settled.** The seam is built and
empty precisely so the answer can come first, and an adapter that exists will make the question
feel academic. It is not: publication is the door with no undo, and the reason that list is
literal is that three payload types arrived one audit apart before anybody noticed.

The operator should make this call. Bring both options with their costs, not a recommendation
dressed as a summary.

## 1. What is already built for you, and needs no design

**The seam.** `mendel_forge/ports.py`:

```python
class HoleFiller(Protocol):
    def fill(self, hole: Hole, observation: Observation) -> FilledValue | None: ...
```

`NoFiller` is the shipped implementation and declines everything. Nothing in the package calls a
filler yet — wiring one is a change to `ops.py`, not to any of the primitives.

**Provenance, end to end, with no new fields.** This is the part most likely to be redesigned
by somebody who did not check:

- `Filler.MODEL` already exists in `scaffold.py`, beside `HAND` and `DERIVED`.
- `FilledValue.by` already carries who settled it — a username for a hand fill, `nf-core` for a
  derived fact, and **a model id** for a model fill.
- `assemble._drafted_by()` already reads that and writes it into `Provenance.drafted_by`, a field
  every contract in the registry has carried since the first one.

So a model-filled contract lands in the registry with the model named in the file, and **no
artifact schema changes at all.** Check this before designing anything: `_drafted_by` is six
lines and it is the whole story.

**Candidates are already a closed choice.** `candidates.for_field` reads the layer stack, and
`Hole.legal` refuses a value outside the list with `MF0003`. A model asked *which of these
twenty-two declared types* cannot invent a twenty-third — invariant 7, enforced when the value is
written rather than when the file is read. This is the single most valuable thing Phase 1 gives
Phase 2, and it is why `--no-ai` being the only mode did not make Phase 1 a detour.

**A hole with no candidates is free text** — `priority_because` has no enumerable domain. Those
are the holes where a model can genuinely invent, and they are the ones worth reviewing hardest.

**`Observation.prose` is what a filler reads.** It is populated and unused today: the nf-core
source puts `meta.yml`'s description and its input/output blocks there. That is deliberate — it
is the evidence a reviewer would read to answer a hole, which makes it the evidence a model
should be given and nothing more.

## 2. Three things that will look like blockers and are not

**`MD0225` and `AiProvenance` do not constrain the forge.** `materialise.py` hardcodes
`ai=AiProvenance(available=[], used=[])` and `MD0225` refuses a value claiming a model settled
it. That guards `pipeline.yml`, which is a *build artifact*. The forge writes *registry files*,
whose `Provenance.drafted_by` is a different field in a different document. **The two never
meet.** This was checked when Phase 1 was scoped and it is why a forge-only phase was coherent;
re-deriving it will cost an hour.

**Invariant 2 is not in tension with a model filling holes.** It says AI authors artifacts
offline, humans approve, runtime is pure lookup. A model filling holes *is* the offline
authoring; `land` refusing the default branch is the approval. Nothing about Phase 2 touches the
resolver's runtime, and invariant 4 — a tier-3 miss never calls a model inside tier 3 — is
untouched because the forge is not in that path at all.

**Determinism is not claimed for the forge and never was.** "Same goal in → same pipeline out"
is about the resolver and compiler. The forge's golden test
(`packages/mendel-forge/tests/test_golden.py`) pins the *derived* scaffold, which has no model in
it and must stay that way — a model-filled draft is not golden-testable and should not be. Keep
the golden fixture on the `NoFiller` path.

## 3. Decisions Phase 2 has to make, which Phase 1 deliberately did not

- **Which holes may a model fill at all?** Everything, or only the ones with candidates? The
  conservative position is defensible: a closed choice is checkable and free prose is not, and
  `priority_because` written by a model is exactly the kind of plausible-sounding reason this
  project exists to avoid. **My view, for what it is worth: start with candidate-bearing holes
  only.** It is the half where the model's output can be validated mechanically.
- **Is a model fill presented as an answer or as a proposal?** `fill` today is immediate and
  persistent. A model fill that lands the same way makes the review a diff review; one that lands
  as a suggestion needs a state `Hole` does not have. The second is more honest and is more work.
- **What do the three protection profiles mean here?** `guarded` is the default and *shows the
  payload and waits for confirmation* — for the prompt door. The forge has no equivalent today.
  Under `sealed`, does the forge simply not call a model? That reads right, and it is not
  written down anywhere.
- **How does a laboratory get a model?** Invariant 12: no subscription OAuth, API keys or local
  models only. Invariant 13: self-hosted is not a degraded tier, so Ollama and vLLM behind an
  OpenAI-compatible endpoint must work identically. One LiteLLM adapter, as
  `docs/design/federation.md` and `CLAUDE.md` both already say.
- **Does `mendel-ai` own the adapter, or does the forge?** `mendel-ai` does not exist yet and is
  specified as implementing `mendel_resolver.ports`. The forge's `HoleFiller` is a different
  protocol in a different package. One LiteLLM client behind both is the obvious answer and
  nobody has written it down.

## 4. Two known weaknesses that Phase 2 will feel

**`Excerpt.text` is weaker than its own docstring asks for.** The nf-core source sets one excerpt
per fact reading `"FASTQC in main.nf"` rather than quoting the line the fact came from, because
`ModuleSpec` records no line numbers. A human clicks through; **a model given that string learns
nothing.** The right fix is in `ModuleSpec` — conformance diagnostics would gain line numbers at
the same time, which is worth more than the forge's share of it. Consider doing this *before* the
filler, because it changes the quality of the filler's input more than any prompt will.

**Rung 4 is a transcription check for a generated module.** Contract and module descend from one
`Observation`, so agreement proves the two code paths match, not that either is right. This gets
worse the moment a model is writing the module's script body: today `MF0005` marks it unfilled
and refuses, and a model that writes a plausible command line produces a module that launches and
does the wrong thing, with `-stub-run` unable to see it. **`MF0005` is load-bearing.** If a
filler is ever allowed near the script body, the ladder needs a rung it does not have.

## What a fresh reader gets wrong

**"A scaffold is a partially-filled contract."** It is not, and the whole design rests on that.
`ModuleContract` validates and forbids extras, so a partially-valid contract is *unrepresentable*
— and it must stay that way, because the moment one is constructible somebody persists one. The
forge holds an `Observation` plus a list of `Hole`s and calls `contract_from` only when the last
hole is filled. The consequence is worth stating plainly: **the forge cannot emit an invalid
declared file.**

**"The holes are wherever the author thought a value was missing."** They are
[`notes/audits/2026-08-16-forge-derivability.md`](../audits/2026-08-16-forge-derivability.md),
implemented literally — a field-by-field measurement against all twelve shipped contracts, kept
as a test so it re-runs. Where that table and the code disagree, the table is right.

**"`--no-ai` is a flag."** Not in the forge. `ports.py` ships `NoFiller`, which declines every
hole, so there is nothing to switch off and nothing to leave accidentally on.

## What the derivability survey actually found

All six of the plan's assertions passed on the first run — which would have made the table an
unmeasured pass, so the per-contract data was dumped and read. **Two rows the plan had guessed
were wrong:**

- **A contract's input port name is not the module's channel name.** Four of twelve rename:
  `SAMTOOLS_INDEX`'s channel is `input` and the port is `bam`; featureCounts' is `bams`; both
  MultiQC contracts rename `multiqc_files`. The pattern is not arbitrary — the contract name says
  *what the channel carries* and the module's says *what the process calls it*. That is the
  semantic overlay `CLAUDE.md` calls the missing 40%, turning up in a field nobody had counted.
- **An output port name is one of up to nineteen.** Every contract declares exactly one output;
  `STAR_ALIGN` offers nineteen emit channels. The set is readable, the choice is not.

`params[].name` split cleanly and mechanically: `via: positional` names an input channel (3 of 3),
`via: ext` never does (3 of 3). Three assertions now hold those findings so they fail in either
direction.

**No shipped contract turned out to be wrong**, then or later.

## What the re-derivation test found

Ten of twelve shipped contracts re-derive from their vendored module exactly — `nf_process`,
`nf_include` and `container` all match, and every shipped output port name appears among the
derived emits. The other two are `comeni/` contracts over vendored modules, which no adapter can
re-read; `forge check` reports them **by name** rather than folding them into the pass, because a
contract nothing checks looks exactly like a contract that agrees.

**No issue was filed, because nothing disagreed.**

## Five corrections to the plan

Written down because `notes/README.md` says to expect them, and because two of them were found by
running the thing rather than by reading it.

**1. The diagnostics ownership guard was blind to every non-`MD` prefix, and the blindness was
not symmetric.** `EMISSION` matched `MD\d{4}`, so `test_every_emitted_code_is_declared` let an
undeclared `MF9999` through. The plan predicted both directions would be silently green and
scheduled the fix for Task 12. In fact `test_every_declared_code_is_emitted` compares the whole
registry against the same scan, so declaring the first `MF` code turned it red **falsely** within
the minute — the code was emitted and the scan could not see it. Task 12 was pulled forward into
Task 4; deferring would have left the gate red for eight tasks. The pattern is now
`[A-Z]{2}\d{4}`, and `test_the_scan_sees_every_declared_prefix` checks it against the registry's
own prefixes rather than a hand-kept list.

**2. A draft could report no holes and still produce a contract with no input ports.**
`scaffold_for` created no `consumes[]` holes at all, so `is_complete()` was true while rung 4
refused with `MD0102` — a contract declaring zero channels for a process that takes one. This is
the worst shape a bug can take here, because it makes the package's headline property false: a
"complete" scaffold that cannot become a contract. **Found by running the documented loop end to
end while writing the guide**, not by any test — every test was green, because every fixture had
been hand-written with its ports already in place. One port hole pair per module input channel
now, with the module's channel names as candidates for the name.

**3. Evidence locators were absolute paths.** The first golden scaffold written carried
`/home/<user>/…/.worktrees/forge-phase-1/vendor/modules/nf-core/fastqc/main.nf` in every fact,
making the golden file machine-dependent and putting the author's checkout into every draft.
Caught by *reading the generated file before committing it*, which is what the plan told the
executor to do and is the same way issue #46's machine-dependent layer digest was found. Locators
are relative now, and `test_no_locator_is_an_absolute_path` holds it.

**4. `Hole.legal` rejected every legal answer for a list field.** `roles` and `produces[].state`
hold several values from one closed set, so the candidates are legal *members*, not legal
*values* — comparing the whole list refused `["qc_per_sample"]` while accepting the bare string.
Found by `ops.fill` on its first real call, which is the argument for building the operations
layer over the primitives rather than after them.

**5. Two smaller ones.** `tools/generate_diagnostics_doc.py` refuses a `concern` with no heading,
which the plan did not anticipate — three new headings. And the plan's `explain` test asserted on
the `says:` line, which `explain` does not print: it renders the code and the `explanation`, for
every code in the project. The test now asserts what the function does.

## Something worth deciding, not fixed here

**`mendel explain` never shows the `fix:` field.** It prints the code and the `explanation`, and
`fix:` — arguably the most actionable part, and the field every `Diagnostic` is required to carry
— is readable only by opening `diagnostics.yml` or the generated page. That is true of all
sixty-odd `MD` codes as much as the new `MF` ones, so the forge should not answer it alone. Worth
an issue.

## Two weaknesses that are in the code rather than here

Both are in `verify.py`'s module docstring, where somebody changing that file will meet them.

**Rung 4 is a transcription check when the module was forge-generated.** The contract and the
module descend from one `Observation`, so their agreement proves the two code paths match, not
that either is right. It is a real check only against a vendored module, where the module is
foreign ground truth.

**Rung 5 warns rather than refuses**, because a laboratory adding a tool before the goal that
needs it is being reasonable.
