## OpenAPI, which the plan under-specified

The operator's instruction was to use OpenAPI properly, and the plan's Task 3 declared the route
bare. Left alone, FastAPI would have named the operation `answer_questions_answer_post` and
documented the 422 with its own `HTTPValidationError` shape — while the route returns
`{"detail": "MF0003: …"}`. **The generated client would have typed the one message a curator
must read as the wrong thing.**

Now: every operation carries an `operationId`, a tag and a summary; the refusal is a declared
`Refusal` model; and `test_openapi.py` holds all four literally, so adding a route means editing
a test that says what the schema promises.

**One thing was tried and reverted, and it is worth carrying.** Declaring the 422 as
`Refusal ∪ HTTPValidationError` is the truthful shape — both arrive at that status. It cannot be
written cleanly: `HTTPValidationError` is a raw dict inside FastAPI rather than an importable
model, so the union has to be a hand-rolled `anyOf` beside the `$ref` FastAPI emits from
`model`, and the two **merge into one schema carrying both keywords**, which generators render
wrongly. The declaration is `Refusal` alone, the caveat is written on the constant, and
`test_the_refusal_schema_is_a_bare_ref` fails if anyone reintroduces the sibling.

**The forge's own transport has the same gap and was left alone.** `mendel_forge.http` answers a
coded refusal correctly and says nothing about it in its document. Closing that is a phase 2
question, not a phase 0 one.

## Two deviations beyond OpenAPI

**The `ValueError` handler is app-level**, as `mendel_forge.http` does it, rather than the plan's
try/except per route. Two transports over one operation must not disagree about a status code,
and a per-route catch is the second spelling that drifts.

**`AnswerInput` and `Answered` come from `schema.d.ts`**, not hand-written as the plan had them.
Re-declaring a type that `make client` generates is the one edit that makes generating it
pointless. `Queue`'s inline `fetch` was folded into the shared client for the same reason.

## Five plan corrections

1. **The router test needed `QueryClientProvider` around `RouterProvider`**, mirroring
   `main.tsx`. Without it the ErrorBoundary caught *"No QueryClient set"* — a green boundary
   over a broken tree, which is the failure this phase exists to stop shipping.
2. **Three assertions matched text the design legitimately uses twice** — `Forge` as both
   wordmark and workspace tab, and `MF0003` in both the message and the `forge explain` hint.
   Each was the test being loose, not the UI being wrong.
3. **The plan says `eslint`; this frontend lints with `oxlint`.** The Vite 8 template ships it.
4. **`oxlint`'s native binding was missing** — npm/cli#4828, the second instance in this
   frontend after rolldown. It is a direct devDependency now, and **CI may need the same.**
5. **Making the row a `Link` broke five slice-1 tests** that rendered `QueueRow` bare. They
   gained router context; the row kept the link.

## What a fresh reader gets wrong

**"Phase 0 is done."** Six tasks of seven, and the missing step is the exit criterion itself.

backend was never driven from the browser in this session.

**"Phase 0 is the forge."** It is the shell plus one action. Phases 1–7 are the queue's filters,
answering properly, proposals, contracts, drift, drafting and compose — spec §3.
