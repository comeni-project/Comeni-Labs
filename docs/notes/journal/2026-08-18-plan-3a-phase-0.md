## The defect the browser found, and no test could

**Every `/forge/*` URL 404'd.** The frontend owns `/forge/queue`, `/forge/contracts` and the rest
as browser routes; `mendel-api` mounts the forge's ASGI transport at `/forge`. On one origin the
dev proxy resolved that collision in the API's favour, so a hard load of the queue never reached
the SPA at all.

**It is invisible to the entire test suite, and that is the interesting part.** Client-side
navigation never leaves the app, so every route test passes and `/` → `/forge/queue` renders
correctly. Only a refresh or a pasted link fails — which is exactly step 3 of the exit criterion,
*copy that URL and open it in a new tab*. Written into the plan before any of this existed.

The API now serves under `/api` — `/api/questions`, `/api/health`, `/api/forge` — and `ROOT` in
`client.ts` is the one place that knows. It removes the collision **class**, not this instance.

## OpenAPI, which the plan under-specified

The plan declared the route bare. FastAPI would have named the operation
`answer_questions_answer_post` and documented the 422 with its own `HTTPValidationError` shape,
while the route returns `{"detail": "MF0003: …"}` — **the generated client would have typed the
one message a curator must read as the wrong thing.**

Now every operation carries an `operationId`, a tag and a summary; the refusal is a declared
`Refusal` model; `test_openapi.py` holds all four literally. All three refusal paths were driven
against the real forge and come back 422 with the code intact — `MF0003` for an illegal value,
`MF0002` for a field that is not a hole, and the reason check for a blank `why`.

**One thing was tried and reverted, and it is worth carrying.** Declaring the 422 as
`Refusal ∪ HTTPValidationError` is the truthful shape — both arrive at that status. It cannot be
written cleanly: `HTTPValidationError` is a raw dict inside FastAPI rather than an importable
model, so the union becomes a hand-rolled `anyOf` beside the `$ref` FastAPI emits from `model`,
and the two **merge into one schema carrying both keywords**, which generators render wrongly.
The declaration is `Refusal` alone, the caveat is on the constant, and
`test_the_refusal_schema_is_a_bare_ref` fails if anyone reintroduces the sibling.

**`mendel_forge.http` has the same gap and was left alone** — it answers coded refusals correctly
and documents none of them. That is phase 2's question, not phase 0's.

## What you still cannot do

Phase 0 ends with **one action** working. Saying so is the correction to slice 1's checkpoint.

- **The queue has no filters, no sort control and no grouping.** `?band=`, `?group=`, `?sort=`
  and `?since=` are in the route table and nothing reads them — phase 1.
- **There is no `answer-all`.** A question asked by three drafts must be answered three times.
  Phase 2, and it is not a wrapper: it needs its own refusal semantics for a partial failure.

  `MODEL` marker. The designed screen is phase 2.
- **No proposals, no contracts, no drift, no sources.** Phases 3–6. Their nav entries render
  `aria-disabled` with the phase that builds them, rather than as links going nowhere.
- **No landing page.** `/` redirects to the queue for the whole of 3A; the landing is 3B.
- **No AI anywhere.** `forge fill --model` exists on the CLI and nothing in the interface calls it.

## Six plan corrections

1. **The router test needed `QueryClientProvider` around `RouterProvider`.** Without it the
   ErrorBoundary caught *"No QueryClient set"* — a green boundary over a broken tree.
2. **Three assertions matched text the design legitimately uses twice** — `Forge` as wordmark and
   as workspace tab, `MF0003` in both the message and the `forge explain` hint. The tests were
   loose; the UI was right.
3. **The plan says `eslint`; this frontend lints with `oxlint`.**
4. **`oxlint`'s native binding was missing** — npm/cli#4828, the second instance here after
   rolldown. It is a direct devDependency now, and **CI may need the same.**
5. **Making the row a `Link` broke five slice-1 tests** that rendered `QueueRow` bare. They gained
   router context; the row kept the link.
6. **A stale `uvicorn` from an earlier session held port 8000** and served pre-change code, so the
   new route 404'd while its tests passed. Check `pgrep -af uvicorn` before believing a 404.
