## 1. What the forge is, and why it is the thing being built now

Mendel resolves a goal against declared data. **It is only as good as the declared data**, and
today that data is a test fixture that happens to be true: a handful of contracts, a dozen
measurements, one shipped rule. Every one of them was written by hand.

The forge is the tool that makes declared data exist in quantity without abandoning what makes it
worth having. Its whole philosophy is one sentence:

> **Make it easy to create and maintain the registry, and catch the errors early — the way the
> compiler already does for pipelines.**

That second clause is what separates this from a code generator. `mendel build` refuses a contract
that disagrees with its module, and it does so with a coded diagnostic that names the file, the
fact contradicted, and what to write instead. The forge points that same machinery at a draft,
before it is a file anyone has to review.

**Why now, and not the rule drafter.** Tier 3 is the differentiator, and
[`2026-08-13-the-rule-drafter.md`](2026-08-13-the-rule-drafter.md) is the component that produces
tier-3 rules. Two of its four hard prerequisites are now met — twenty corpus rules exist in
`tests/fixtures/rule-corpus/`, and Plan 1.15 reformed the format against them. One is half met:
the measurement floor is closed and nothing writes a measurement. **The fourth needs a corpus of
real tier-4 flags, which needs Mendel run on real data, which needs Plan 3.** So the drafter stays
where its spec put it, and the forge builds the part that has ground truth available today: a tool
source is checkable, and literature is not.

## 2. Scope, and what was deliberately pushed out

### Phase 1 — deterministic

Everything in this spec unless marked otherwise. No model is called; **`--no-ai` is not a flag,
it is the only mode**, which keeps it honest by construction rather than by discipline.

### Phase 2 — the model fills holes

Same subsystem, one port implemented. §10 is the seam and §10.3 is the invariant question it must
answer first. **Phase 2 does not get designed here** beyond the shape Phase 1 must leave for it.

## 3. The spine: sources, observations, scaffolds, holes

### 3.1 The load-bearing decision

**A scaffold is not a half-built contract.** `ModuleContract` has validators and
`extra="forbid"`; a half-contract is *unrepresentable*, and it must stay that way, because the
moment a partially-valid contract is constructible somebody will persist one.

So the forge holds an **`Observation`** — what was proven from the source — plus a list of
**`Hole`s**, and constructs the real `ModuleContract` only when the last hole is filled.

**The consequence is the property the whole design rests on: the forge can never emit an invalid
declared file.** It emits either a valid one, or something that is honestly not one yet and says
which fields it is missing and why.

### 3.2 The three types

```
Source (Protocol)
  name       SourceName
  discover(root)  -> list[ToolRef]        what is ingestible here
  ingest(ref)     -> Observation          what can be proven about one tool
```

```
Observation                    source-neutral, evidence-bearing, no opinions
  facts   dict[FactName, Fact]  process name, container, input arity, emits, meta keys…
  prose   list[Excerpt]         documentation, for a human now and a model in Phase 2
                                every Fact carries Evidence(locator, excerpt) —
                                a file:line or a URL, never a bare assertion
```

```
Scaffold                       a partial artifact with typed holes
  kind         DeclaredKind     what it will become
  target       str              path within the layer
  observation  Observation
  filled       dict[FieldPath, FilledValue]   value + filler + why
  holes        list[Hole]

Hole
  field       FieldPath         "produces[0].type_id"
  what        str               what is needed, in one sentence
  why_open    str               why it could not be derived
  candidates  list[Candidate]   what the registry already declares
  evidence    list[Excerpt]     the source text bearing on it
  filled_by   Filler | None     hand | derived | model:<id>
```

### 3.3 `candidates` is the hint mechanism, and it is also an invariant

For a `type_id` hole, `candidates` is the vocabulary's declared types; for `roles`, the declared
roles. **It is the same list three ways** — printed by the CLI, rendered as a picker by the GUI,
handed to Phase 2's model as a closed choice rather than an open prompt.

That last one matters more than convenience. Invariant 7 says vocabularies are closed, and a
closed candidate list is that invariant enforced at *draft* time rather than discovered at *load*
time. A model asked "which of these nine types" cannot invent a tenth; a model asked "what type is
this" can and will.

### 3.4 The two sources are asymmetric, and the design admits it

| | nf-core | pegi3s (#65) |
|---|---|---|
| Nextflow module | ships `main.nf` | **none — the forge generates one** |
| process, input arity, emits, meta keys | derived by `modulespec.py` | holes |
| container | derived | derived |
| semantic `type_id`, `state`, `roles` | holes | holes |

The nf-core adapter is largely `ModuleSpec` read *forwards* rather than backwards — the same
parser conformance already uses to check a contract, used to propose one.

**A source that ships no module is what forced §4 into existence.** Had the protocol been designed
against nf-core alone it would have assumed a module exists, and pegi3s would have arrived later
as a rewrite rather than an implementation. This is why #65 is a phantom limb rather than a
deferral: **planned for, load-tested by a fixture (§9.3), and not built.**

## 4. Module generation

For a source with no Nextflow module, the forge writes a skeleton `main.nf` beside the contract:
process name, container, input and output declarations, the `versions.yml` block and a `stub`
block. **The script body is a hole**, because it is not derivable and pretending otherwise is the
failure this project exists to be an alternative to.

Two things follow that a plan must handle rather than discover.

- **`nf_include` must point at a file that exists**, or the pipeline cannot emit. A contract whose
  module the forge generated points at the generated module, and the two land together or not at
  all.
- **Conformance over a generated module is weaker than over a vendored one** — see §5, rung 4.

## 5. The verification ladder

Cheapest first. Every rung emits the `Diagnostic` shape that already exists in
`mendel_compiler/conformance.py` — `code`, `where`, `summary`, `detail`, `fix` — because a
diagnostic without a `fix` is half a diagnostic, and because one shape means one renderer.

| # | Rung | Asks | Codes |
|---|---|---|---|
| 1 | complete | any holes left? | `MF`, new |
| 2 | constructs | does the Pydantic model validate? | `MF`, new, wrapping `ValidationError` |
| 3 | loads | `layers.load()` with the draft stacked over the registry | `MD0001`–`MD0009`, reused |
| 4 | conforms | `conformance.check` against the module | `MD0100`–`MD0108`, reused |
| 5 | routes | does anything in the layer reach it? | `MF`, new |

**Four of five rungs are machinery that already exists**, pointed at a draft instead of a build.
That is the argument for this shape over a bespoke validator: a second implementation of "is this
contract sound" would disagree with the first one within a plan.

Two honest weaknesses, recorded rather than left to be found:

- **Rung 4 is a transcription check for a generated module, not an independent one.** Contract and
  module descend from one `Observation`, so agreement between them proves the two code paths
  match, not that either is right. It still catches real bugs. It is not the guarantee it is for a
  vendored nf-core module, where the module is foreign ground truth.
- **Rung 5 is the inert case arriving early.** A contract nothing can route to changes nothing —
  the rule drafter's §5.2 problem, one level down. A reviewer should learn that before landing,
  not after.

`forge verify` runs the ladder. **`forge land` runs it first and refuses on any refusing
diagnostic.**

## 6. One operations layer, three transports

Every verb is one function, pydantic in, pydantic out:

```
def verb(req: VerbRequest) -> VerbResult
```

- **CLI** — argv → request, result → renderer. `--json` emits the result model verbatim.
- **HTTP** — JSON → the *same* request, the *same* result → JSON. A mountable ASGI app under
  `mendel_forge/http/`, so Plan 3's `mendel-api` inherits it rather than duplicating it.
- **GUI** (Plan 3) — calls the HTTP one. No third model to learn.

Neither transport holds logic. A new verb is one function plus two thin adapters, and the CLI's
`--json` output is byte-identical to the HTTP response — which is what makes the console the
honest preview of what the GUI will show, and what lets an agent drive the forge and get exactly
the diagnostics a human sees.

### 6.1 The verbs

| Verb | Does |
|---|---|
| `forge sources` | registered sources |
| `forge discover --source nf-core` | what is ingestible |
| `forge draft <ref>` | ingest → scaffold → workspace |
| `forge show <draft>` | the scaffold, its holes, its diagnostics |
| `forge fill <draft> <field> <value>` | fill a hole by hand |
| `forge verify <draft>` | the ladder |
| `forge check` | re-ingest on-disk sources, diff against the registry |
| `forge update <id>` | turn a diff into a draft |
| `forge land <draft> --registry <path>` | branch and commit into a registry checkout |

`forge check` and `forge update` are the **maintain** half. They answer *"does the registry still
match the source on disk"* — offline, no network. *"Has the tool moved on"* is #64.

## 7. Landing: invariant 2 across a repository boundary

Invariant 2 says the forge drafts and **a person approves; nothing writes to the registry
automatically.** Since issue #46 the registry is a separate repository, and since
comeni-registry#1 there is no `contracts/` directory to move a file into — a layer is files that
declare their own kind, arranged freely. So the old wording — *"only human approval moves a file
from `proposals/` to `contracts/`"* — describes a layout that no longer exists.

**The workspace is the queue.** Drafts live outside the registry: one directory per draft holding
the scaffolded files plus a record of the source, the holes, the diagnostics, the provenance and
the diff. It is what the CLI reads, what the HTTP layer serves, and what the Plan 3 GUI renders.

**`forge land` is the boundary, and it is deliberately narrow.** It writes into a registry checkout
on a **new branch**, never the default branch, never into a dirty tree, and **nothing else in
`mendel-forge` writes to a registry path at all** (§9.4 is the guard).

**Opening a pull request is an optional convenience, never a requirement.** A lab landing into a
private local overlay gets the identical path — invariant 13 says self-hosted is not a degraded
tier, and making GitHub the approval mechanism would break it.

## 8. Diagnostics

New codes are **`MF`, `emitted_by: forge`** — the prefix is already reserved in
`comeni_core/diagnostics.yml`'s header for exactly this.

**A code is declared in `diagnostics.yml` and emitted through `coded()` in the same change.**
`tests/test_diagnostics_ownership.py` holds both directions, so a reserved-but-unemitted band
fails CI. **The forge cannot reserve an `MF` range ahead of use** — this is one of the three things
the old Plan 2 could not have known.

Reused codes keep their existing prefix and owner. A draft failing rung 3 emits `MD0004` because
that is what it *is*; inventing an `MF` twin would mean two codes for one condition and a runbook
that cites the wrong one.

## 9. Testing

In order of how much each would catch.

### 9.1 Re-derive the shipped registry

Ingest every vendored nf-core module and assert the scaffold's **filled** fields match the
hand-written contracts in `registry/tools/nf-core/`. **This is real ground truth that exists
today**, and any disagreement is a finding either way — either the ingester is wrong or a shipped
contract is. No other test available to this subsystem is as strong.

The count is not written here. The test derives it from the tree, for the reason A71 and A72
exist.

### 9.2 Golden scaffolds

Source in → exact `Scaffold` JSON out, the same discipline as the golden `.nf`. **Determinism is a
test here too**: the same source must produce a byte-identical scaffold, hole order included.
`frozenset` has no stable order and neither does a dict built by iteration — anything that
serialises a set needs the `field_serializer` treatment `IREdge.states` already has.

### 9.3 The fixture source

A pegi3s-*shaped* fake in the test suite: container and name only, every other field a hole,
script body a hole, module generated. A dozen lines, no network.

**It exists so the `Source` protocol has two implementations from the first commit.** A protocol
with one implementation is a protocol designed against imagination — the rule drafter's §1
argument, applied here.

### 9.4 A watched-failing guard on the write boundary

Nothing in `mendel-forge` writes to a registry path except `land`. **Delete the guard and it must
fail loudly**, and the revert goes in [`notes/audits/guard-ledger.md`](../audits/guard-ledger.md)
with the message it printed. A14's standard: a guard never watched failing may be inert rather
than merely weak.

## 10. Phase 2 seams — built now, left empty

### 10.1 The port

```
# mendel_forge/ports.py
class HoleFiller(Protocol):
    def fill(self, hole: Hole, obs: Observation) -> FilledValue | None: ...
```

It returns the **same `FilledValue`** a human's `forge fill` produces — value, filler, why — so a
model-filled hole and a hand-filled one are the same shape, differing only in `filler`. `None` is
a filler declining, which must stay legal: a filler that always answers is a filler that invents.

Phase 1 ships `NoFiller`. Phase 2 ships a LiteLLM-backed filler — **one adapter, any provider**:
Anthropic, OpenAI, or a local model over an OpenAI-compatible endpoint (Ollama, vLLM both
qualify), which is invariant 13 again.

### 10.2 Provenance is already there

`Filler` records `hand`, `derived` or `model:<id>`, and `land` copies it verbatim into
`Provenance.drafted_by` — a field `ModuleContract` has carried since the first contract and
`mendel docs` already renders. **Phase 2 wires a model without touching the artifact's provenance
design at all.**

### 10.3 The finding: Phase 2's model call is a fifth egress door

> **Resolved 2026-08-17: there is no door 5.** See
> [`2026-08-17-forge-phase-2.md`](2026-08-17-forge-phase-2.md) §1. The argument below is
> preserved because it is the argument that got the question asked, and because the resolution
> turns on a distinction it did not draw — that the doors track the **prompt taint path**
> (`docs/design/clinical-data-protection.md` §4.2) rather than all data. `DOORS` and
> `tests/test_egress.py` did not change.


`DOORS` in `comeni_core/artifact/egress.py` is `goal_extraction`, `tier4_resolution`,
`compiler_repair`, `publication`. **A forge sending module source and documentation prose to a
model is none of them**, and invariant 14 says there are four and no others.

The payload is public open-source text rather than laboratory data, so the argument for opening
the door is easy. **That is not the same as the door being open.** Invariant 14's entire point is
that widening the boundary means deliberately editing a test that says *these are all the ways
data leaves* — and the list has now put this question in front of somebody six times.

**This is Phase 2's first task, not its first surprise.** It is written here because the last plan
for this subsystem was overtaken by exactly this class of thing: a guard built after the plan,
which refused what the plan intended to produce.

### 10.4 What Phase 2 still does *not* touch

`AiProvenance` and `MD0225` guard `pipeline.yml` — the *build artifact* recording that a model
settled a value. The forge writes *registry* files. **The two never meet**, and conflating them is
what made the old Plan 2 look blocked when the forge half never was.

## 11. What this spec deliberately does not decide

- **Which model, and how prompted.** Phase 2's problem, and it would be decided wrong now.
- **How a landed contract is versioned when a source bumps.** #64 raises it: a contract id carries
  `@version`, a higher layer sharing a module key displaces lower ones, and a bump is therefore a
  new contract rather than an edit. Which one a draft represents is that issue's question.
- **Whether the workspace is ever shared between people.** Phase 1's is local. A curator queue
  serving several reviewers is a Plan 3 question, and `docs/design/forge-review.md` already has
  the screens for it.
- **How a contract is retired.** The rule drafter's §7 asks the same question about rules and it is
  unanswered for both.

## 12. The one-paragraph version

The forge ingests a tool from a pluggable source, proves every fact it can from the source itself,
and turns everything it cannot prove into a typed hole carrying what is known, why it is open, and
which declared values would be legal there. It generates the Nextflow module too when the source
does not ship one. It runs a five-rung ladder — complete, constructs, loads, conforms, routes —
built mostly from machinery the compiler already has, and refuses to land anything a rung refuses.
A human fills the holes, and in Phase 2 a model proposes fills that a human still approves.
Landing writes to a branch in a registry checkout and nothing else in the package writes there at
all. It never emits an invalid declared file, because a half-built contract is not a type it can
construct.
