# 14.7.4 part 4 — The consultant's words — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this
> plan task by task, in one hand. Tick each `- [ ]` as it completes; deviations go in the
> execution record.

**Goal:** Scenario 1 reads like a person talking — an acknowledgement after the first sentence,
each question phrased for the person and pre-filled with what they already said, a read-back
written from the composed goal, invented constraints offered as suggestions — while no pipeline
value is recorded that the person did not confirm.

**Architecture:** Two new queued model calls on the AI worker, both split (part 3) and counted
(part 1): `builder.ask.v1` phrases a gap and may name an answer already given; `builder.readback.v1`
writes the card's sentence from the composed goal. Results are stored on the session and on the
pending proposal, and the page sees them through its **existing poll**, which now also runs while
a pending gap or card is waiting for its words. The want prompt becomes `builder.goal.v6`: an
acknowledgement instead of a summary, and constraints stored as suggestions.

**Tech stack:** Python 3.12, FastAPI, SQLAlchemy, arq jobs; React 19 + TanStack Query + Vitest.

**Spec:** [`docs/superpowers/specs/2026-09-29-the-consultants-words-design.md`](../specs/2026-09-29-the-consultants-words-design.md) §7, §9 (walk).
**Issues:** #167 #176 #186 under 14.7.4 (#180). Runs after parts 1–3.

## Global constraints

- **Asynchronous, never chatty:** every model call is a queued job (`jobs.AI_QUEUE`), keyed so a
  duplicate collides (`job_id_for`); enqueued from the async layer (a route or a job), never from
  sync service code; the page learns results through its one existing poll.
- **Only the person's click makes a fact.** `already` pre-fills; a suggested constraint is kept
  only by the person.
- **A refused, failed or stale phrasing changes nothing visible** beyond keeping the engine's words.
- **Born split** (part 3's divider and `render_split`); **counted** (part 1's `session_id`).
- **Recorded replies in tests, never a live model.** Each check in its own call before a commit.

## Rulings made while planning

- **The want prompt is `builder.goal.v6`** (part 3 made v5 the split of v4's content).
- **Phrasing is keyed by gap subject, not proposal id:** the prefetch runs before the next gap's
  proposal exists. Results live in the session's goal dict under `phrased` (`{subject: {asks,
  already_option, already_value}}`); `as_goal` drops the key, like `summary`/`stated`.
- **The poll's new reason to run** is a pending proposal whose words are still coming
  (`Question.phrasing == "pending"`, `GoalSummary.readback_pending`), so no new timer exists.
- **`in_flight`** in the usage total counts pending turns and pending words, from the same fields.

## Review focus

1. **The person answers before the phrasing lands:** the late result is stored for nobody and the
   answered gap is untouched; the next gap still uses its own prefetch. Task 4.2.
2. **`already` names an option the gap did not offer, or a value the declaration refuses:** it is
   dropped and `asks` still used (MI0205/MI0208 are recorded on the call row, not shown). Task 4.2.
3. **No model configured:** no phrasing job is queued, `phrasing` is `"none"` from the start, and
   the poll does not run for it. Task 4.2.
4. **A stop (*I don't have one*) right after a prefetch:** the prefetched phrasing is wasted — one
   counted call, nothing shown. Task 4.2.
5. **The person edits the card while the read-back is still coming:** the read-back describes the
   offered goal and is labelled as the AI's; the chips are what gets built. Task 4.3.
