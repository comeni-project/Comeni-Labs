# Wiener W2 — reading a run without reading text

> **For agentic workers:** REQUIRED SUB-SKILL: use `superpowers:executing-plans`, driven by the
> operator's own session, task by task. **Do NOT use `subagent-driven-development`** — `CLAUDE.md`
> forbids farming out implementation. Tick each `- [ ]` as it completes, and where a step was
> carried out differently, tick it anyway and record the deviation in the execution table.

**Goal:** the run page opens on one row per process rather than four hundred rows of text, with
every §9.3 comparison on it, and the builder's draw → keep → gate → run becomes one visible
sequence.

**Architecture:** one pure per-process projection in `wiener-core` — `stats()` grown into
`overview()` rather than a second one beside it — served by one endpoint, rendered by a table
whose every bar shares its column's scale. Tasks are paged from the `run_task` projection with
`ORDER BY`, never folded per request. The console keeps its shape and stops being the default.

**Tech Stack:** Python 3.12 · Pydantic · FastAPI · SQLAlchemy + Alembic · React 19 · TypeScript ·
Tailwind 4 · `@tanstack/react-query` · `@tanstack/react-virtual` (new).

**Spec:** [`../specs/2026-08-24-w2-reading-a-run.md`](../specs/2026-08-24-w2-reading-a-run.md).
**Read it before Task 1.** Every `§` below is that document's unless it says `wiener.md`.
The screens are drawn: [`../../docs/design/w2-mockups/`](../../docs/design/w2-mockups/), nine

## Global constraints

- **`wiener-core` is PURE** — invariant 1. No network, no subprocess, **no clock**. A separate
  scan holds `datetime.now` out of it.
- **`overview()` takes `Sequence[str]`, not a `Pipeline`.** The declared process names are what it
  needs; taking the artifact type would put `comeni_core.artifact` into a fold that does not need
  it. `wiener-api` passes `[step.process for step in pipeline.steps]`.
- **Absence is `None`, never `0`.** `ProcessStats` already does this and the docstring says why.
  Nothing in the UI may turn a `None` into a zero.
- **No number without a source.** No percentage over a discovered denominator (§5), no rate on a
  live edge (`wiener.md` §9.2), no threshold the interface invented (§4.1).
- **Four tables, still.** `test_the_store_is_four_tables` stays at four; W2 adds **columns** to
  `run_task`, which is a projection and exists to be queried.
- **`make check` is the gate.** No task here touches `resolve.py`, `router.py`, `rules/`,
  `mendel_compiler/cli/`, `emit.py` or `artifact/pipeline.py`, so **`make verify` is not
  required** — except Task 4, which changes `frontend/src/tokens.css`, where the frontend suite
  is the gate instead.
- **The frontend gate is `npx tsc -b && npx vitest run && npm run lint`**, run from `frontend/`.
  That is what CI runs.
- **`make client` after any route change.** Never hand-edit `frontend/src/api/` or
  `frontend/src/wiener/api/`.
- **Diagnostic codes:** Wiener's band is `MW0001`–`MW0099`. `MW0001` and `MW0002` are taken. W2
  needs none; if one becomes necessary, declare it in `comeni_core/diagnostics.yml` and run
  `make docs`.

## The pre-execution audit — A191–A200, 2026-08-24

Run before Task 1, **against the code and against the live database** rather than against the
spec. Nine findings; **three change the plan's shape** and are folded into the tasks below rather
than left as warnings.

What the audit *checked and cleared*, so nobody re-derives it: `Attempt` carries all eight
resource fields the projection reads; `nullslast()` is still valid in SQLAlchemy 2.0.52;
`json_array_length(attempts)` runs against the real column, which is `json` and not `jsonb`;
`ix_run_task_process` and `ix_run_task_status` genuinely exist in the database and not only in the
model; the four-table guard keys on `__tablename__` so new **columns** do not trip it; and the
samplesheet guard is a blocklist of column *names* that the three new ones do not collide with.

**A191 — CRITICAL. The Tasks tab cannot sort on a resource without new columns.**
`run_task` indexes `process` and `status` and keeps `attempts` as a **JSON blob**. Filtering is
therefore SQL and cheap; *sorting by memory across the run* is not — it would mean loading 5,000
JSON documents to order them. The spec's §10.1 says "sorted server-side" and the schema cannot
honour it. **Task 3 adds three derived columns** — `peak_rss_bytes`, `realtime_ms`, `pct_cpu` —
written by the projection that already writes the row, with an index on the first two. It is a
migration and no new table, so the four-table guard is untouched. This is the same argument
`CLAUDE.md` already makes about ranking at scale being `ORDER BY`.

**A192 — CRITICAL. `/overview` must degrade where `/graph` 404s.**
`routes/runs.py::graph` answers `404 "this run's artifact cannot be read"` when
`_artifact_pipeline` returns `None`. The overview must **not** copy that: counts are folded from
events and are worth showing even when the artifact is gone, and a 404 on the default view turns a
readable run into a blank page. Task 2 returns `steps_declared: 0` and `declared: false` on every
row instead, and a test holds it.

**A193 — renaming `/stats` is a three-file change or CI goes red.**
`Stats.tsx` and `Stats.test.tsx` are its only consumers, plus the generated
`frontend/src/wiener/api/schema.d.ts`. Deleting the route without deleting both leaves `tsc -b`
failing on a missing schema member. Task 6 does all three in one commit.

**A194 — `dashboard.md` §2 claims authority over `tokens.css`.**
That file's header says the document is authoritative and the file mirrors it. Adding `--hover`,
`--t`, `--ring` and the four Depth tokens to the file and not the document makes the header false.
Task 4 edits both.

**A195 — a new dependency means the lockfile, and CI runs `npm ci`.**
`@tanstack/react-virtual` must land in `frontend/package.json` **and** `package-lock.json` in the
same commit, or the frontend job fails on a lockfile that does not match.

**A196 — the artboards' hover CSS is not the product's.**
`docs/design/w2-mockups/build.py` is a design tool and nothing imports it. Task 4 writes the
tokens into `frontend/src/tokens.css` **by hand**, from the spec's §12.1 — do not copy the
artboard's `<style>` block, which also carries mockup-only classes.

**A197 — Wiener has no operation-id guard, and W2 adds two routes.**
`mendel-api` holds every `operationId` in a literal list — `test_every_operation_is_named_by_hand`
— so adding a route means editing a test. **`packages/wiener-api/tests/` has no equivalent.** A
route added without `operation_id=` would ship as `run_overview_api_runs__run_id__overview_get`
into the generated client and nothing would object. W2 adds `/overview` and `/tasks`, which is the
moment to add the guard rather than the moment to notice it is missing. **Task 2 adds
`packages/wiener-api/tests/test_wiener_openapi.py`** holding all eleven operations literally.

**A198 — `Float` is not imported in `models.py`.**
Its imports are `JSON, BigInteger, DateTime, Integer, String, Text`. Task 3's `pct_cpu` column
needs `Float` added to that line — noted because a plan step that does not compile is the kind of
thing this audit exists to catch, and it cost ten seconds to check.

**A199 — `useRunStream`'s events array is unbounded and W2 makes that matter.**
At 5,000 tasks the hook holds ~15,000 objects and re-creates the array on every message —
`setEvents((seen) => [...seen, event])` is O(n) per event, so the tail degrades quadratically as
the run grows. Task 10 batches arriving events into one state write per animation frame. Left
alone, the console gets slower the longer you watch it, which is the opposite of what W2 promises.

**A200 — RESOLVED. Nothing in the fold can name a sample, and nothing in it ever will.**

The artboards show `sample_07` on every task row, the failure banner names it, and §12.3's menu
copies the work directory and the task hash. **None of the three exists in the projection.**
`TaskTrace` admits `tag`, `name`, `hash` and `workdir` — every one marked `LabString` — and
`fold()` keeps *none* of them: `TaskState` has `process`, and `Attempt` has resources and
timestamps.

**That is not an oversight, and putting them there fails a guard written to catch exactly this.**
`test_the_fold_is_where_the_lab_strings_stop` says so in its own docstring:

> Adding `script` to `TaskState` — which somebody will want for the console one day — reopens the
> path, and this fails rather than the leak shipping.

W2 is that day. §8's claim that no lab string can become a span attribute is **structural** today
— they are not in the fold at all — and option 1 below would downgrade it to a rule somebody has
to remember.

| | what it costs |
|---|---|
| **1. Put `tag`/`hash`/`workdir` on `TaskState`** | fails the existing guard, and §8 stops being structural. **Not recommended** |
| **2. `wiener-api` reads them from `run_event.payload` when serving `/tasks`** | boundary perfect, `wiener-core` never sees a lab string — but a page of tasks means scanning the run's events, and a 5,000-task run has ~15,000 of them |
| **3. A `labels` JSON column on `run_task`, written by the impure projection** | fast and `wiener-core` stays clean — but a **sample tag becomes a queryable column**, which is precisely what §7.1's guard argues against: *"a column is where a thing gets queried, joined and exported"* |
| **4. No tags — identify a task by `task_id`** | costs nothing and loses the thing that makes a row mean something to a biologist |

**RESOLVED 2026-08-24 by the operator: option 3.** It was put as a recommendation for option 2
and the operator asked the right question — *are we sure, and is the guard fair?* — which found a
mistake in the ranking.

**The guard is fair, and it is kept.** Its own docstring says why better than the audit did:
*"`script`, `workdir`, `name` and `tag` are exactly the fields a backend would happily index and
retain."* The risk is not theoretical — the collector's exporter is a **config file** a laboratory
can point at any OTLP backend, §16 says plainly that Wiener stands in patient data, and a FASTQ
tag is often an accession number. Telemetry is the one path where lab data leaves silently.

**But the guard protects `wiener-core`, and options 2 and 3 both keep lab strings out of it
entirely** — the projection lives in `wiener-api`, which is impure and already holds the whole
trace. Option 3 does not weaken the guard by a line; `test_the_fold_is_where_the_lab_strings_stop`
passes untouched.

**And the §7.1 objection against option 3 was overstated.** §7.1 forbids a table holding *the
samplesheet's contents* — the list of samples the laboratory submitted, which rides to the
launcher as a job argument and is never stored. A per-task tag is not that: it is what Nextflow
reports about a task, and it is **already** in `run_event.payload`, a column sitting next door.

So option 3 wins on cost with no boundary given up. **The residual, stated rather than hidden**: a
`labels` column makes tags conveniently queryable — `WHERE labels->>'tag' = …` — in a way that
scanning a JSON payload technically already permits but does not invite. That is a small, real
increase in exposure and it is written here so nobody discovers it later as a surprise.

**Task 3 grows a fourth column**, `labels`, written from the raw payload by the projection.
**Task 5's `TaskView` carries `tag`**, and Tasks 9 and 11 may rely on it.

```python
class ProcessRow(BaseModel):
    model_config = ConfigDict(frozen=True)

    process: str
    declared: bool = False
    """In the artifact. **False means the run ran something the pipeline does not describe** —
    which happens when an artifact cannot be read (A192), and must not be silently hidden."""
    reached: bool = False
    """Any task of it has been seen. `declared and not reached` is the not-started row."""

    tasks: int = 0
    done: int = 0
    running: int = 0
    failed: int = 0
    cached: int = 0
    attempts_max: int = 1

    memory_asked_bytes: int | None = None
    memory_peak_bytes: int | None = None
    cpus_asked: int | None = None
    cpu_used_pct: float | None = None
    realtime_ms: int | None = None
    queue_wait_ms: int | None = None
    read_bytes: int | None = None
    write_bytes: int | None = None


class Overview(BaseModel):
    model_config = ConfigDict(frozen=True)

    rows: tuple[ProcessRow, ...] = ()
    steps_declared: int = 0
    """From the artifact. **The only honest denominator** — §5: Nextflow discovers tasks as
    channels emit, so a task-level percentage is a number nobody can source."""
    steps_finished: int = 0
```

```python
def overview(state: RunState, declared: Sequence[str]) -> Overview:
    """Per process, worst case kept, in the order the artifact declares.

    **Declared order, not sorted.** The pipeline's shape is what a reader is orienting by, and
    a table that reorders itself as a run progresses cannot be scanned twice.
    """
    by_process: dict[str, list[TaskState]] = {}
    for task in state.tasks.values():
        by_process.setdefault(task.process, []).append(task)

    # Declared first, in order; then anything the run ran that the artifact does not describe.
    names = list(declared) + [p for p in by_process if p not in set(declared)]

    rows = tuple(_row(name, name in set(declared), by_process.get(name, [])) for name in names)
    finished = sum(
        1 for row in rows
        if row.declared and row.reached and row.running == 0 and row.tasks > 0
    )
    return Overview(rows=rows, steps_declared=len(declared), steps_finished=finished)
```

```python
def _row(process: str, declared: bool, tasks: list[TaskState]) -> ProcessRow:
    attempts = [a for task in tasks for a in task.attempts]
    return ProcessRow(
        process=process,
        declared=declared,
        reached=bool(tasks),
        tasks=len(tasks),
        done=sum(1 for t in tasks if t.status in ("COMPLETED", "CACHED")),
        cached=sum(1 for t in tasks if t.status == "CACHED"),
        failed=sum(1 for t in tasks if t.status in ("FAILED", "ABORTED")),
        running=sum(1 for t in tasks if t.status in ("RUNNING", "SUBMITTED")),
        attempts_max=max((len(t.attempts) for t in tasks), default=1),
        memory_asked_bytes=_worst([a.memory_bytes for a in attempts]),
        memory_peak_bytes=_worst([a.peak_rss_bytes for a in attempts]),
        cpus_asked=_worst([a.cpus for a in attempts]),
        cpu_used_pct=_worst([a.pct_cpu for a in attempts]),
        realtime_ms=_worst([a.realtime_ms for a in attempts]),
        queue_wait_ms=_worst([
            a.duration_ms - a.realtime_ms
            for a in attempts if a.duration_ms is not None and a.realtime_ms is not None
        ]),
        read_bytes=_worst([a.read_bytes for a in attempts]),
        write_bytes=_worst([a.write_bytes for a in attempts]),
    )
```

```python
class OverviewOut(BaseModel):
    rows: list[dict] = []
    steps_declared: int = 0
    steps_finished: int = 0


@router.get("/runs/{run_id}/overview", operation_id="readOverview",
            summary="One row per process the artifact declares")
def run_overview(run_id: str) -> OverviewOut:
    """**It does not 404 on an unreadable artifact** — A192, and deliberately unlike `/graph`.
    The counts come from the fold and are true whatever happened to the directory; what is lost
    is the declared list, so every row says `declared: false` and the bar has no denominator.
    """
    with db.session_scope() as session:
        if repository.run(session, settings.lab_id, run_id) is None:
            raise HTTPException(status_code=404)
        pipeline = _pipeline_of(session, run_id)
        state = state_of(session, settings.lab_id, run_id)

    declared = [step.process for step in pipeline.steps] if pipeline is not None else []
    got = overview(state, declared)
    return OverviewOut(
        rows=[row.model_dump(mode="json") for row in got.rows],
        steps_declared=got.steps_declared,
        steps_finished=got.steps_finished,
    )
```

```python
def tasks_page(session, lab_id, run_id, *, process=None, status=None, retried_only=False,
               sort="task_id", after=0, limit=100):
    query = (select(RunTask)
             .where(RunTask.lab_id == lab_id, RunTask.run_id == run_id)
             .order_by(SORTS.get(sort, SORTS["task_id"]), RunTask.task_id)
             .offset(after).limit(min(limit, 500)))
    if process:
        query = query.where(RunTask.process == process)
    if status:
        query = query.where(RunTask.status == status)
    if retried_only:
        query = query.where(func.json_array_length(RunTask.attempts) > 1)
    return list(session.scalars(query))
```

- **Every declared process had a row from the first poll**, including at `0/0` before anything
  started: `finished 0/4  STAR_GENOMEGENERATE:0/0  STAR_ALIGN:0/0  SAMTOOLS_SORT:0/0

  three of them never reached.
- **`steps_finished` went 0 → 1 → 4 and never down.** It is **not monotonic in general** and
  cannot be, which is pinned by a test rather than left to be discovered: Nextflow discovers
  tasks as channels emit, so a step with three tasks done is finished until a fourth is
  submitted. The alternative — remembering that a step was once finished — is monotonic and
  false. **The interface must not draw this as a bar that only fills** (Task 7).
- **Absent is `None` and a real zero is `0`**, both present in the same run:
  `SUBREAD_FEATURECOUNTS` reported `realtime_ms: 0` because it took under a millisecond, and
  every unreached row reported `None`. That is the distinction the projection exists to keep.
- **`-peak_rss_bytes` sorted correctly**: STAR_ALIGN 1.27 GB → SAMTOOLS_SORT 39 MB →
  SUBREAD_FEATURECOUNTS 28 MB → STAR_GENOMEGENERATE 3.8 MB, with `tag` populated (`test`,

counted a process whose every task FAILED, so `0d3a4e3d` read **2 of 5 finished with zero
successes** — the one honest bar advancing on failure. Fixed in `fff0dcd`; the rule is now
`done == tasks`.
