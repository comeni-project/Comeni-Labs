# 2026-08-17 — the forge, Phase 1: built

The second entry today. [`2026-08-17.md`](2026-08-17.md) handed Plan 2 over for redesign; this
one reports the plan that replaced it, executed end to end.

## Where things stand

**`mendel-forge` exists, and it calls no model.** Twenty-three tasks, seven checkpoints, all
run. `make verify` is green. The package is the first entry in `IMPURE_PACKAGES`, and
`test_no_pure_package_imports_an_impure_one` holds the arrow pointing at the pure packages and
never back.

The loop is `discover → draft → show → fill → verify → land`, over one operations layer with two
transports. [`docs/guides/driving-the-forge.md`](../../docs/guides/driving-the-forge.md) is that
loop with real output; `ARCHITECTURE.md` §10 is the description against the types;
[`the spec`](../specs/2026-08-16-the-forge.md) is why each part is shaped the way it is.

**What is next: Phase 2, and its first task is not an implementation task.** A forge model call
sends tool documentation to a provider, and invariant 14 says data leaves through *four* declared
doors. Either the forge's call is a fifth and the invariant's number changes, or it is not egress
and the argument for that has to be written down. §10.3 of the spec sets the question up; nobody
has answered it. **Do not write a `HoleFiller` implementation before it is answered** — the seam
is built and empty precisely so that the answer can come first.

## What a fresh reader gets wrong

**"A scaffold is a partially-filled contract."** It is not, and the whole design rests on that.
`ModuleContract` validates and forbids extras, so a partially-valid contract is *unrepresentable*
— and it must stay that way, because the moment one is constructible somebody persists one. The
forge holds an `Observation` plus a list of `Hole`s and calls `contract_from` only when the last
hole is filled. The consequence is worth stating plainly: **the forge cannot emit an invalid
declared file.**

**"The holes are wherever the author thought a value was missing."** They are
[`notes/audits/2026-08-16-forge-derivability.md`](../audits/2026-08-16-forge-derivability.md),
implemented literally — a field-by-field measurement against all twelve shipped contracts, kept
as a test so it re-runs. Where that table and the code disagree, the table is right.

**"`--no-ai` is a flag."** Not in the forge. `ports.py` ships `NoFiller`, which declines every
hole, so there is nothing to switch off and nothing to leave accidentally on.

## What the derivability survey actually found

All six of the plan's assertions passed on the first run — which would have made the table an
unmeasured pass, so the per-contract data was dumped and read. **Two rows the plan had guessed
were wrong:**

- **A contract's input port name is not the module's channel name.** Four of twelve rename:
  `SAMTOOLS_INDEX`'s channel is `input` and the port is `bam`; featureCounts' is `bams`; both
  MultiQC contracts rename `multiqc_files`. The pattern is not arbitrary — the contract name says
  *what the channel carries* and the module's says *what the process calls it*. That is the
  semantic overlay `CLAUDE.md` calls the missing 40%, turning up in a field nobody had counted.
- **An output port name is one of up to nineteen.** Every contract declares exactly one output;
  `STAR_ALIGN` offers nineteen emit channels. The set is readable, the choice is not.

`params[].name` split cleanly and mechanically: `via: positional` names an input channel (3 of 3),
`via: ext` never does (3 of 3). Three assertions now hold those findings so they fail in either
direction.

**No shipped contract turned out to be wrong**, then or later.

## What the re-derivation test found

Ten of twelve shipped contracts re-derive from their vendored module exactly — `nf_process`,
`nf_include` and `container` all match, and every shipped output port name appears among the
derived emits. The other two are `comeni/` contracts over vendored modules, which no adapter can
re-read; `forge check` reports them **by name** rather than folding them into the pass, because a
contract nothing checks looks exactly like a contract that agrees.

**No issue was filed, because nothing disagreed.**

## Five corrections to the plan

Written down because `notes/README.md` says to expect them, and because two of them were found by
running the thing rather than by reading it.

**1. The diagnostics ownership guard was blind to every non-`MD` prefix, and the blindness was
not symmetric.** `EMISSION` matched `MD\d{4}`, so `test_every_emitted_code_is_declared` let an
undeclared `MF9999` through. The plan predicted both directions would be silently green and
scheduled the fix for Task 12. In fact `test_every_declared_code_is_emitted` compares the whole
registry against the same scan, so declaring the first `MF` code turned it red **falsely** within
the minute — the code was emitted and the scan could not see it. Task 12 was pulled forward into
Task 4; deferring would have left the gate red for eight tasks. The pattern is now
`[A-Z]{2}\d{4}`, and `test_the_scan_sees_every_declared_prefix` checks it against the registry's
own prefixes rather than a hand-kept list.

**2. A draft could report no holes and still produce a contract with no input ports.**
`scaffold_for` created no `consumes[]` holes at all, so `is_complete()` was true while rung 4
refused with `MD0102` — a contract declaring zero channels for a process that takes one. This is
the worst shape a bug can take here, because it makes the package's headline property false: a
"complete" scaffold that cannot become a contract. **Found by running the documented loop end to
end while writing the guide**, not by any test — every test was green, because every fixture had
been hand-written with its ports already in place. One port hole pair per module input channel
now, with the module's channel names as candidates for the name.

**3. Evidence locators were absolute paths.** The first golden scaffold written carried
`/home/<user>/…/.worktrees/forge-phase-1/vendor/modules/nf-core/fastqc/main.nf` in every fact,
making the golden file machine-dependent and putting the author's checkout into every draft.
Caught by *reading the generated file before committing it*, which is what the plan told the
executor to do and is the same way issue #46's machine-dependent layer digest was found. Locators
are relative now, and `test_no_locator_is_an_absolute_path` holds it.

**4. `Hole.legal` rejected every legal answer for a list field.** `roles` and `produces[].state`
hold several values from one closed set, so the candidates are legal *members*, not legal
*values* — comparing the whole list refused `["qc_per_sample"]` while accepting the bare string.
Found by `ops.fill` on its first real call, which is the argument for building the operations
layer over the primitives rather than after them.

**5. Two smaller ones.** `tools/generate_diagnostics_doc.py` refuses a `concern` with no heading,
which the plan did not anticipate — three new headings. And the plan's `explain` test asserted on
the `says:` line, which `explain` does not print: it renders the code and the `explanation`, for
every code in the project. The test now asserts what the function does.

## Something worth deciding, not fixed here

**`mendel explain` never shows the `fix:` field.** It prints the code and the `explanation`, and
`fix:` — arguably the most actionable part, and the field every `Diagnostic` is required to carry
— is readable only by opening `diagnostics.yml` or the generated page. That is true of all
sixty-odd `MD` codes as much as the new `MF` ones, so the forge should not answer it alone. Worth
an issue.

## Two weaknesses that are in the code rather than here

Both are in `verify.py`'s module docstring, where somebody changing that file will meet them.

**Rung 4 is a transcription check when the module was forge-generated.** The contract and the
module descend from one `Observation`, so their agreement proves the two code paths match, not
that either is right. It is a real check only against a vendored module, where the module is
foreign ground truth.

**Rung 5 warns rather than refuses**, because a laboratory adding a tool before the goal that
needs it is being reasonable.

## The guards
