# Plan 3 — the API and the dashboard, thinly

**Status:** deliberately thin design spec, written 2026-08-18 with the operator.

**Why it is thin, and why that is the point.** Plan 3 consumes the types
[`2026-08-18-the-shared-question.md`](2026-08-18-the-shared-question.md) is about to move.
Specifying it in detail now would be writing against types that do not exist yet — which is
precisely why the original Plan 2 was **deleted rather than corrected** on 2026-08-16, and why
`notes/README.md` says every plan in this repository has needed correction during execution.
This file records the **decisions**, so they are not re-litigated. The detail is written after
Plan 2.5 lands, against the code.

`notes/plans/2026-08-02-mendel-api-and-dashboard.md` is the existing nine-task plan. It is
**stale in the same way Plan 2 was** — written 2026-08-02, before most of the types it
references — and this spec supersedes its ordering and its first task. Its file structure,
endpoint sketch and frontend component breakdown are still useful raw material.

---

## 1. What Plan 3 is for

A researcher — or an agent — describes what they want, Mendel resolves it deterministically, and
**the questions it could not answer deterministically are reviewed on screen**. The red/yellow
triage is the product's whole point; everything else is transport.

**Audience, decided:** the operator's own iteration loop first, a demo shortly after. So the
review surface is built before the pipeline graph, and rough is acceptable where it does not
require undoing to show.

## 2. The decisions already taken

Recorded here so they are not re-argued when the detailed plan is written.

- **Full stack, as the original plan specifies** — FastAPI, SQLAlchemy 2.0, Alembic, ARQ, Redis,
  Postgres, React 19, TypeScript, Vite, Tailwind 4, Docker Compose. A files-and-synchronous
  alternative was offered and declined on 2026-08-18: the destination is a hosted multi-user
  service, and the stack is that destination's.
- **OpenAPI-first, non-negotiable.** The TypeScript client is **generated** from `openapi.json`
  and committed; `frontend/src/api/` is never hand-edited. This is what makes it impossible for
  the IR types to drift between backend and frontend, and it is the reason FastAPI was chosen
  over Django in the first place.
- **Vertical slice, then broaden.** Not tasks 1→9 in order. A thin end-to-end path — one build,
  one endpoint, one screen — lands first, then each layer widens. The operator's stated goal is
  *"have all the moving parts interacting so we can iterate"*, and that is the definition of a
  slice. It also surfaces the stale-plan corrections while they are cheap.
- **Plan 3 absorbs the tier-4 ambiguity resolver**, decided 2026-08-17. Invariant 6 flags tier 4
  *even at high model confidence*, so a model answer never removes the human — it saves them
  composing a reply. Resolver and review screen are one feature.
- **Issue [#69](https://github.com/comeni-project/Comeni-Labs/issues/69) is the first design
  task, not an assumption.** `AiProvenance.available` is hardcoded `[]` and `MD0225` refuses the
  first model-backed build.
- **The rule drafter runs after Plan 3**, moved on 2026-08-18. The recorded argument for putting
  it first optimised for *queue size*; what the project is short of is *feedback*, and nothing
  currently renders a tier-4 queue to look at.

## 3. Task 1 is an extraction, not a scaffold

**The original plan's core assumption is false.** It says `mendel-api` is *"a thin FastAPI skin
over the existing packages"* with *"no business logic in route handlers"*. Both are right as
intentions, but **there is no build function to be thin over**.

The whole build orchestration lives inside `resolve_verbs.run(args, parser)`
(`packages/mendel-compiler/src/mendel_compiler/cli/resolve_verbs.py:39`): it takes an argparse
`Namespace`, loads layers, runs conformance, calls `resolve()`, writes `pipeline.yml`, calls
`emit()` and `emit_config()`, runs the gate, prints to **stderr** and returns **exit codes**.
The pieces underneath are clean and reusable; the orchestration is CLI-shaped end to end.

An API route could shell out to the CLI — losing typed errors, losing progress, and inheriting a
contract of exit codes and stderr text — or reimplement the sequence, giving two orchestrations
that drift, one of which is the path `tests/test_counts.py` guards.

**So the first task lifts the orchestration into a callable** in `mendel-compiler` taking typed
inputs and returning a typed result or raising coded errors. The CLI verb becomes its first
caller; printing and exit codes stay in the CLI where they belong. The API becomes its second.
`make verify` then still guards the path the API uses, which shelling out would quietly have
ended.

**It will not be as thin as the original plan hoped, and the honest goal is "as thin as
possible".** Stating that up front is better than discovering it at task 4.

## 4. One schema, two consumers

`OpenQuestion` — one API schema that both `Hole` and `Ambiguity` project into, published in
`openapi.json`.

- **The React review queue** renders it as a card: what is being asked, why it is open, the
  candidates, the evidence, and — once settled — who answered and why.
- **An agent driving Mendel over HTTP** GETs the same route, receives the same JSON, decides, and
  POSTs answers back.

There is **no separate agent API**. That was settled on 2026-08-18 when the operator chose
*"agent drives Mendel via the API"* over *"agent writes pipeline code Mendel scaffolds"* — the
second would have put model output into the emitted artifact and required restating *"same goal
in → same pipeline out"*. The first leaves determinism untouched: everything derivable is
derived before the agent sees anything, exactly as the forge already works.

The projection lives in `mendel-api`. It is a DTO, not a door payload, so the §5 rules of the
Plan 2.5 spec do not reach it.

## 5. Constraints carried from the original plan

Still correct, and load-bearing:

- **The dashboard never accepts a sample sheet, a filename or a path.** Invariant 15. *"Let the
  user upload their samplesheet"* is a natural feature request and it would end the guarantee.
  Sample identity belongs to the laboratory's execution environment and reaches the pipeline
  through `params.input` at run time.
- **No business logic in route handlers.** Routes validate, dispatch, serialise.
- **Long work runs in ARQ, never in a request.**
- **Telemetry stays opt-in and off by default**, and can only exist in `mendel-api` — invariant 1
  makes that structural rather than a promise.
- **This plan implements structure and behaviour, not visual design.** The `frontend-design`
  skill runs after it lands.

## 6. What is not decided yet

Named as open rather than guessed, to be settled against the code once Plan 2.5 lands.

- The slice boundary — exactly which entity, endpoint and screen constitute slice one.
- Whether the first screen renders build ambiguities, forge holes, or both.
- Auth. The original plan has none, and a hosted multi-user service needs one.
- Whether the prompt door (door 1, plain-language → `Goal`) appears in Plan 3 at all or follows
  it. The operator's sequencing on 2026-08-18 puts it *after* the GUI; the original plan's
  Task 3 assumes the build worker accepts a prompt.
- The `guarded` protection-profile confirmation gate. Issue
  [#71](https://github.com/comeni-project/Comeni-Labs/issues/71) says the profiles are
  implemented in zero lines, and the original plan requires the gate be real rather than a toast.

## 7. Estimate

Two to three weeks for the nine tasks at this repository's standard, after Plan 2.5's three to
five days. Recorded before starting, per `CLAUDE.md`'s *"stop and speak when the estimate
breaks"* — an estimate wrong by more than about double is a decision point, and the number is
easier to argue with now than at 1am.
