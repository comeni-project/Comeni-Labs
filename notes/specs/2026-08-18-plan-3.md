# Plan 3 — the API and the interface

**Status:** design spec, written 2026-08-18 with the operator, against the code that exists and
the interface that was drawn. Replaces `2026-08-18-plan-3-thin.md`, which was deliberately thin
because it preceded both the design and Plan 2.5.

**Precedence:** where this spec and the code disagree, the code is right and this file has drifted.

**Read first:** [`docs/design/forge-review.md`](../../docs/design/forge-review.md) — the forge's
ten screens and the reasoning behind each; [`docs/design/dashboard.md`](../../docs/design/dashboard.md)
— the Mendel builder and, in §2, the token, type and spacing system that governs both halves.

---

## 1. What Plan 3 is

Put both halves of the product behind an HTTP surface and build the interface that was designed:
the **Mendel builder** (canvas, provenance, settings, review) and the **Forge** (queue,
contracts, sources).

**It is mainly interface work, and it is not only a frontend.** §4 is the list of things that must
exist underneath for the screens to be true rather than decorative, and that list is the reason
this spec is long.

**The original `2026-08-02-mendel-api-and-dashboard.md` is superseded.** It predates the types it
references, its screens predate the design, and its central premise is false — see §3.

---

## 2. The stack

FastAPI · SQLAlchemy 2.0 · Alembic · ARQ · Redis · Postgres · React 19 · TypeScript · Vite ·
Tailwind 4 · TanStack Query · vitest · Docker Compose.

**Unchanged from the 2026-08-02 plan, and two calls were raised and decided on 2026-08-18.**
Recorded because a decision without its argument gets re-litigated:

- **Postgres from day one**, rather than deferring it. The argument against was that at MVP it
  holds ~2 thin tables: the registry is files by decision ([issue #43](https://github.com/comeni-project/Comeni-Labs/issues/43)),
  `pipeline.yml` *is* the artifact, and with no accounts *"since my last visit"* is a
  `localStorage` timestamp. **The operator kept it**: the destination is a hosted multi-user
  service, and a migration later costs more than the infrastructure now.
- **Tailwind 4, configured with our tokens.** The argument against was that the mockups are
  already plain CSS with custom properties and they work. **The operator kept it**, so Tailwind's
  `@theme` mirrors the six type roles and the nine-step spacing scale, and those scales stay
  authoritative. The bespoke parts — dashed and gapped tier strokes, orthogonal SVG wire routing,
  the origin-stripe gutter — drop to plain CSS regardless; utilities are the wrong tool for them
  and forcing them through Tailwind is how the design would drift from `dashboard.md`.

**OpenAPI-first is non-negotiable.** The TypeScript client is generated from `openapi.json` and
committed; `frontend/src/api/` is never hand-edited. That is what makes it impossible for the IR
types to drift between backend and frontend, and it is why FastAPI was chosen.

## 3. What already exists — and one premise that is false

### The forge's HTTP transport is built

`packages/mendel-forge/src/mendel_forge/http/__init__.py` is **a real mountable ASGI app** with
eleven routes covering the whole loop: `/sources`, `/discover`, `/drafts`, `/drafts/list`,
`/drafts/show`, `/drafts/fill`, `/drafts/fill-with-model`, `/drafts/verify`, `/drafts/land`,
`/check`, `/update`.

Its own docstring names this plan:

> **It binds nothing and has no auth.** Phase 1 ships an `app` object; Plan 3's `mendel-api`
> mounts it and owns the questions this file deliberately does not answer — who is calling, over
> what, and whether they may.

Every route is three lines, no route contains an `if`, and `tests/test_http.py` compares the CLI
and HTTP payloads directly. **So the forge half is mostly mounting, not building.**

### The build path has no equivalent, and "a thin skin" is false

The 2026-08-02 plan says `mendel-api` is *"a thin FastAPI skin over the existing packages"*. There
is no build function to be thin over. The whole orchestration lives inside
`resolve_verbs.run(args, parser)` (`packages/mendel-compiler/src/mendel_compiler/cli/resolve_verbs.py:39`):
it takes an argparse `Namespace`, loads layers, runs conformance, calls `resolve()`, writes
`pipeline.yml`, calls `emit()` and `emit_config()`, runs the gate, prints to **stderr** and returns
**exit codes**.

An API route can shell out to the CLI — losing typed errors and progress, inheriting a contract of
exit codes and stderr text — or reimplement the sequence, giving two orchestrations that drift,
one of which is the path `tests/test_counts.py` guards. Neither is acceptable, so §4.1 is Task 1.

## 4. What must exist underneath

The screens are drawn. This is what has to be true for them to mean anything. **Each entry names
the screen that needs it**, so nothing here is speculative infrastructure.

### 4.1 Build orchestration, lifted out of the CLI

*Needed by: every Mendel screen.*

A callable in `mendel-compiler` taking typed inputs and returning a typed result or raising coded
errors. The CLI verb becomes its first caller — printing and exit codes stay in the CLI, where
they belong — and the API becomes its second. `make verify` then still guards the path the API
uses, which shelling out would quietly have ended.

**As thin as possible, but honestly not thin.** Saying so up front beats discovering it at task 4.

### 4.2 `OpenQuestion` — one schema, two consumers

*Needed by: the forge queue, the Mendel review tab, and an agent driving over HTTP.*

Both `Hole` (forge) and `Ambiguity` (build) project into one API schema. Plan 2.5 made them
subclasses of one `Question`, so the projection is nearly free — that was the point of doing 2.5
first.

**Two consumers, not two endpoints.** React renders it as a card; an agent GETs the same route and
POSTs answers back. There is no separate agent API, which is what makes *"the agent drives Mendel
via the API"* cost almost nothing extra.

It lives in `mendel-api`. It is a DTO, not a door payload, so Plan 2.5 §5's egress rules do not
reach it.

### 4.3 Queue aggregation

*Needed by: the queue's `×11` collapsing, which is what keeps it bounded.*

Nothing computes this today. The queue must group open questions by `(subject, suggested answer)`
across drafts so 86 confirmable answers render as a handful of rows. Without it the list grows
linearly with the registry and the design's scaling claim is false.

### 4.4 A consumers index

*Needed by: the registry lookup panel ("consumed by"), the module page ("its output feeds").*

`Registry.producers_of` exists. **There is no `consumers_of`.** It is derivable by scanning
contracts' `consumes[].type_id`, and it wants to be computed once per layer stack rather than per
request.

### 4.5 Which pipelines pin a contract

*Needed by: the module page's "6 published pipelines pin this contract"; the drift screen's
"breaks 6 pipelines", which is the consequence sort's evidence.*

**Nothing tracks this.** A `pipeline.yml` records the contracts it pins, but nothing reads the set
of published pipelines and inverts it. This is the clearest case for Postgres in §2: a table of
published pipelines and the contracts each pins, refreshed on publish.

**Without it the queue's consequence sort has no numbers**, and "drift first" becomes an assertion
rather than a measured cost.

### 4.6 Drift, as something the interface can show

*Needed by: the queue's Drift rows, the contracts list, the module page, the drift screen.*

`ops.check` returns `Drift(contract_id, field, registry_says, source_says)` — field-level, with
both values. That is the right shape and it already exists.

**Two gaps.** It is **offline**: it compares the registry against the *vendored* source, never
against upstream ([#64](https://github.com/comeni-project/Comeni-Labs/issues/64)) — so *"a newer
version is available"* is not yet knowable, and the queue's `Scaffold the bump` action cannot be
honest until it is. And nothing schedules it; the design says *"checked 4 minutes ago · next
nightly"*, which needs an ARQ periodic job and somewhere to store the result.

### 4.7 Whether a drift changes routing

*Needed by: the drift screen's verdict block, the highest-value element in the maintenance half.*

*"Nothing routes differently — `container` is not read by the router"* is a real computation:
does the drifted field participate in routing (type, state, role) or not? It is a small, closed
classification over `ModuleContract` fields, and it must be **derived from the field, not
hardcoded per case**, or it will be wrong the first time a new field is added.

### 4.8 DAG layout

*Needed by: the Mendel canvas, for any pipeline the user did not hand-place.*

`dashboard.md` §9 records this as the largest outstanding piece: **node positions are hand-placed
in the mockup.** A generated pipeline needs layered (Sugiyama-style) assignment with crossing
reduction. Orthogonal wire routing makes crossings more legible but does not reduce them.

**This is the single biggest risk in Plan 3** and the one most likely to be underestimated.

### 4.9 `AiProvenance.available` — issue #69

*Needed by: any model-backed resolution.*

`materialise.py` hardcodes `ai=AiProvenance(available=[], used=[])`, and `MD0225` refuses a value
claiming a model settled it while the build records none was available. **The first model-backed
build is refused today.** Something has to decide what a build knows about its own model access
and where that is threaded from. This is a design task, not a one-line fix, and it comes before
the tier-4 resolver rather than with it.

### 4.10 The tier-4 ambiguity resolver

*Needed by: the Mendel review tab's model-suggested answers.*

Absorbed into Plan 3 on 2026-08-17. Invariant 6 flags tier 4 *even at high model confidence*, so a
model answer never removes the human — it saves them composing a reply. Resolver and review screen
are one feature, and building the resolver without the screen would be building the half that
cannot be checked.

### 4.11 Batch answering

*Needed by: "Accept for all three", and the confirmable list's "Accept the 16 ticked".*

`forge fill` settles one field on one draft. Answering one question across three drafts, or
sixteen questions at once, is a new operation — and it must record the same provenance per value
as a single fill, or the batch path becomes the one that loses the reasons.

### 4.12 Not needed, and worth saying

- **"Since my last visit"** is a `localStorage` timestamp. No accounts, no table.
- **`mendel docs` already generates a Markdown page per tool** from registry data alone. The
  module page is a richer, live version of the same idea — worth reading before building it
  rather than inventing a second traversal of the same data.

## 5. The API surface

Three groups, mounted under one app:

- **`/forge/*`** — mount the existing `mendel_forge.http.app`. Add nothing to it; questions of
  who is calling and whether they may belong to the mount, not the routes.
- **`/builds/*`** — over §4.1's callable. `POST /builds` dispatches an ARQ job and returns an id;
  `GET /builds/{id}` is the result; `GET /builds/{id}/events` is SSE progress.
- **`/questions/*`** — the `OpenQuestion` projection, and the answer endpoint. The one surface
  both React and an agent use.

**No business logic in route handlers.** Routes validate, dispatch, serialise.

**Long work runs in ARQ, never in a request.** A stub gate is up to 900s cold; `-profile test` is
minutes; a model fill over a local model took 227s for one module in the forge's own measurements.

## 6. The frontend

`frontend/` — Vite, React 19, TypeScript, Tailwind 4 with `@theme` mirroring the tokens,
TanStack Query, vitest. **The directory does not exist yet**; `CLAUDE.md`'s architecture block
says so as of 2026-08-18.

Two workspaces and one lookup, exactly as designed:

- **Mendel** — canvas, provenance bar, settings card, three-tab rail
- **Forge** — queue, contracts, sources, and the subpages beneath each
- **Registry** — a panel available from both, never a destination

**The design is the specification.** Where this spec and `docs/design/*.md` disagree about a
screen, the design document is right. What is **firm** and what is **provisional** is
`forge-review.md` §8 — structure is firm, densities and the facet set are not.

**Invariant 15 has a UI face.** The dashboard never accepts a sample sheet, a filename or a path.
*"Let the user upload their samplesheet"* is a natural feature request and it would end the
guarantee. Sample identity belongs to the laboratory's execution environment and reaches the
pipeline through `params.input` at run time.

## 7. Slice order

Vertical, not layer-by-layer. The goal is the moving parts interacting early, so each slice is
end-to-end.

1. **Forge queue, read-only.** Mount the existing forge app, add `OpenQuestion` (§4.2) and
   aggregation (§4.3), render the queue. This is the shortest path to something real because the
   backend is already there.
2. **Answering.** The question screen, the lookup panel, batch answering (§4.11).
3. **Contracts and drift.** The consumers index (§4.4), the routing verdict (§4.7), the module
   page.
4. **Build orchestration (§4.1) and the Mendel canvas**, with DAG layout (§4.8).
5. **Model in the loop.** #69 (§4.9), then the tier-4 resolver (§4.10).
6. **Compose, CI, and the periodic drift check** (§4.6).

**Slice 1 before slice 4 deliberately**, even though Mendel is the product's headline: the forge
has a backend and the builder does not, so slice 1 proves the whole shape — API, generated client,
component, token system — against the half where nothing is blocking.

---

## 8. Explicitly out of scope

- **Auth and accounts.** `--by` is a string; read `git config user.name` and let it be overridden.
  Adding real auth later changes one field's source.
- **The prompt door.** Plain-language → `Goal` is door 1 and follows Plan 3, by the operator's
  sequencing on 2026-08-18.
- **The rule drafter.** Moved behind Plan 3 the same day.
- **The three protection profiles.** [#71](https://github.com/comeni-project/Comeni-Labs/issues/71)
  — documented, implemented in zero lines, and larger than this plan. The `guarded` confirmation
  gate is named in the 2026-08-02 plan and stays unbuilt.
- **Upstream version checking.** [#64](https://github.com/comeni-project/Comeni-Labs/issues/64).
  Its absence is what §4.6 records as a limit on the drift screen's honesty.
- **`Sources`** is in the navigation and undrawn (`forge-review.md` §9). It needs a design pass
  before it needs a plan.

---

## 9. Estimate

**Three to four weeks**, and the range is wider than the thin spec's two-to-three because §4 is
longer than that spec assumed — the forge backend existing pulls it down, and DAG layout,
the pipeline-pin store and #69 push it up.

Recorded before starting, per `CLAUDE.md`'s *stop and speak when the estimate breaks*: an estimate
wrong by more than about double is a decision point, and **§4.8 (DAG layout) is the most likely
place for that to happen.**
